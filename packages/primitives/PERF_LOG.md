# Primitives performance ratchet

## 2026-09-23 — uncached regex compilation

- Scope/runtime: `@wrongstack/primitives` is a shared Node.js library used synchronously by caller processes; metric is wall time per batch of 750 distinct user regex compilations (cache misses), because each compilation blocks the caller. Benchmark exercises the built package export with 750 valid, distinct `(?:fooN|barN)+` patterns. Package correctness baseline: `pnpm exec vitest run packages/primitives/tests` — 6 files / 99 tests passed. Build command: `pnpm --filter @wrongstack/primitives build`.
- Commit: `7196107e09bd366ec438d40f4318992f3eecc315`. Machine: WHITE, Windows x64, AMD Ryzen 9 9950X3D 16-Core Processor; Node v24.13.0. Benchmark source: `.temp_files/perf-ratchet/primitives-20260923/bench.mjs` (round-owned scratch).
- Baseline command (5 separate processes): `for /L %i in (1,1,5) do @node .temp_files/perf-ratchet/primitives-20260923/bench.mjs`. Measurements (ms): 24.6689, 28.9696, 24.9684, 26.7234, 24.6579; min/median/max = **24.6579 / 24.9684 / 28.9696 ms**. Repeat-run spread 4.3117 ms (17.3% of median); required win must exceed this spread and 5%.
- Hypothesis: `hasAmbiguousQuantifiedAlternation` calls `detectQuantifiedAmbiguity` twice with identical content for unprefixed quantified groups (the measured shapes). Skip the second call only when stripped content equals the original. Predict >=20% lower uncached batch median from avoiding one semantic analysis per group; preserve distinct-content behavior for prefixed groups.
- Attempt 1 (one-expression change to `src/regex-guard.ts`): guarded the second ambiguity analysis with `stripped !== inner`. After rebuilding with `pnpm --filter @wrongstack/primitives build`, package tests `pnpm exec vitest run packages/primitives/tests` passed (6 files / 99 tests); `pnpm --filter @wrongstack/primitives typecheck` passed. Same benchmark command, five process runs (ms): 25.0955, 27.9461, 26.5751, 24.4638, 23.2438; min/median/max = **23.2438 / 25.0955 / 27.9461 ms**. Median increased 0.1271 ms (+0.5%) from the 24.9684 ms baseline, far inside the baseline 4.3117 ms spread and 5% floor. **REVERT.** Read in code: duplicate analysis occurred for unprefixed groups. SPECULATIVE: other checks or host scheduling obscured its saving; no CPU profile was run, so the actual time distribution is unknown.
- After reverting, rebuild and package tests passed again (6 files / 99 tests); the same five-run benchmark command yielded 23.6120, 24.4526, 26.6179, 49.4915, 24.2651 ms, min/median/max = **23.6120 / 24.4526 / 49.4915 ms**. Baseline median 24.9684 ms vs reverted 24.4526 ms (apparent -2.1%, inside noise; **zero retained improvement**). The 49.4915 ms outlier confirms the machine was noisy; further small hypotheses are not justified with this setup. Machine load and peer count were not recorded at each measurement, so any between-phase attribution is additionally unverified. No full monorepo tests or profile was run; package tests only. The benchmark scratch source is removed after recording, so the exact command documents the measurement but cannot be rerun without recreating that round-owned source.
