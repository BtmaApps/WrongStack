## Importer and Consumer Tracing

- Resolve a module's full consumer set with one repo-wide grep for the module specifier with optional extension — pattern `name(\.js)?['"]` — which catches re-exports (a re-export line contains the specifier too) and test files, unlike `codebase-incoming-calls`, which needs one query per exported symbol and mis-attributes import rows on shared lines. If the grep result is untruncated, treat the hit list as exhaustive.
- The same specifier grep settles "who imports this test file": Vitest tests under `packages/*/tests/` export nothing, so `codebase-incoming-calls` has no symbols to query, and an untruncated zero-match grep is exhaustive proof the only consumer is the test runner. A test's real coupling surface is its own imports (`../src/*` units under test plus `tests/helpers/`), already listed in its import block.
- The specifier grep has three known failure modes — recognize and adapt:
  - **Directory modules**: in-package deep imports of the form `../src/<name>/index.js` are missed (the `/` after the basename defeats the quote anchor). Widen the pattern to `name(/index)?(\.js)?['"]` and/or pair with `codebase-incoming-calls` on the module's exports.
  - **Short names that double as product-identifier string literals** (e.g. `jev`, `council`): quoted literals in tool registries and enum values produce dozens of false hits. Grep a distinctive exported symbol (e.g. `buildJevCommand` from `packages/cli/src/slash-commands/jev.ts`) in `files_with_matches` mode, or anchor to import syntax: `from ['"].*/name(\.js)?['"]`.
  - **Names that are substrings of other identifiers**: a bare-basename grep for `DependencyDetail` returns false hits from i18n locale keys (`missingDependencyDetail`) and unrelated identifiers. Grep the import-specifier pattern instead: `from ['"].*ComponentName['"]|import\(.*ComponentName`.
- Types modules have a third, dynamic-import channel: files that only use qualified inline types (e.g. `import('./types.js').MemorySourceRef` in `packages/sage/src/domain-term-extractor.ts`) have no static import line and are silently missed by `from`-anchored greps. Beyond `from './types'` / `../types`, also grep `import\(['"](\.{1,2}/)+(src/)?types(\.js)?['"]\)`.
- Sibling and intra-directory consumers use relative specifiers (`./session-lanes`, `./useChatViewState`) that path-style specifier greps never match — include the bare basename in the sweep for these.
- Always run an unbounded `files_with_matches` grep alongside content-mode grep; the content view truncates at the match limit and hides files. Then classify every hit with a scoped read before counting: comment-only mentions, same-named locals in other packages (e.g. `packages/cli/src/slash-commands/theme.ts` defines its own `THEME_OPTIONS`), and doc references are not dependents — only files with an actual `import ... from` line are.
- Scope importer greps to the owning package path when a basename recurs across packages — `slash-commands/index.ts` exists in `packages/cli`, `packages/plug-lsp`, and `packages/telegram`, so an unscoped grep returns cross-package false positives.

## Re-Exporters and Definition Files

- Before mapping a module's consumers, check whether any importer re-exports it (`export type { ... } from '<module>'`). The re-exporter becomes the module's effective public surface: direct-deep-path greps then show zero external importers by design, and cross-package consumers typically reach the module through the package barrel, which deep-path greps never match. Trace outward consumers through the re-exporting file's specifier.
- When `codebase-incoming-calls` returns import rows for a symbol that also flows through a re-exporter, separate direct deep-path importers from re-export consumers with one repo-wide grep for the module basename literal: the direct-importer set is exactly the files whose import lines contain it; remaining symbol-consumer files reach it through the re-export.
- When an import specifier points at a re-exporter, the definition lives elsewhere — grep the symbol name repo-wide to find the defining file before editing. Known instances: `packages/tui/src/theme.ts` re-exports `themePresets` (defined in `theme-presets.ts`) and the types from `theme-types.ts`; `packages/sdd/sdd-parallel-run.js` re-exports `SddSupervisorVerdict`/`SddSubtaskSpec` actually defined in `sdd-parallel-run-types.ts`; `WSSessionsList` is defined in `@wrongstack/webui-protocol` (`webui-protocol/src/conversation-core.ts`) while `packages/webui/src/types/system.ts` only re-exports it.
- For types-only modules, never derive the importer set from `codebase-incoming-calls` alone — it returns only importers of the queried symbols, missing siblings that import unqueried exports. Pair symbol queries with a repo-wide module-path grep (`research/types(\.js)?['"]`) plus a relative-form grep scoped to the owning directory (`from ['"]\./types(\.js)?['"]`).
- For any module under `packages/webui/src/types/`, treat `packages/webui/src/types.ts` (the `@/types` barrel, `export * from './types/*.js'`) as the effective public surface: a specifier grep for `types/<mod>` returns only the barrel plus sibling `./<mod>.js` importers, while the real app-wide consumer set flows through the `WSServerMessage` union in `packages/webui/src/types/server-message.ts` and arrives as `from '@/types'`. Enumerate that chain before judging blast radius.

## Tool Limitations

- `codebase-incoming-calls` cannot see dynamic imports: template-literal dynamic imports like ``import(`./locales/${lng}/${ns}.json`)`` and `React.lazy(() => import('./Name'))` wiring in `packages/webui/src/components/view-registry.ts` both return zero. Grep instead, and check `view-registry.ts` before concluding a WebUI component is dead code.
- When `codebase-incoming-calls` reports "symbol exists in multiple files", grep the symbol name repo-wide before attributing callers — twin implementations exist (e.g. `decodePageCursor`/`PageCursor` in both `packages/sage/src/sqlite-store-pagination.ts` and `packages/sage/src/shared/pagination.ts`), and callers of one are not callers of the other.
- Do not treat `codebase-incoming-calls` import/type_ref entries as call sites — pair with a targeted read of constructors and producer methods to distinguish ownership from usage. Use it only to corroborate grep counts; its import rows can be attributed to the wrong symbol on shared lines.
- Do not trust `codebase-skeleton` on import-dominated composition-root files (e.g. `packages/cli/src/slash-commands/index.ts`, collapsed 215 lines to 1). When the skeleton looks degenerate, fall back to a full `read`.
- The `grep` tool's `pattern` field rejects alternations over 256 chars — split long symbol-name unions into multiple `files_with_matches` greps rather than one; the pieces remain cheap and exhaustive.
- The codebase index never covers the gitignored `.wrongstack/` tree: `codebase-search`/`codebase-context` returning empty there is expected, not evidence of no consumers. The only reliable tracer for a `.wrongstack/` file is a repo-wide grep of its basename.

## `.wrongstack/` Project Kits

- A kit at `.wrongstack/project-kit/<kit>/` is a `main.mjs` exporting `run(input, ctx)` plus a `fixtures/` tree that the kit runner copies wholesale to a scratch dir for `@kit/` roots. Establish a kit's consumer set by running `tree` on the kit directory and reading `main.mjs`; prove zero tracked-code references with a repo-wide grep from the tracked side, confirming the count/truncation flag before claiming zero.
- Before editing any file under `<kit>/fixtures/`, read the sibling `<kit>/kit.json` verification cases first — the declared tests pin exact artifact properties (e.g. `bytes: 13` per file, `scanned: 5` per directory), so a seemingly harmless content edit can break kit verification with zero code-level references to warn you.
- Classify a fixture file by **which `kit.json` list pins it** before judging edit blast radius: `scanned` pins file existence/count, `candidates`/`deleted` entries pin exact `bytes`, and `skipped` entries pin only `path`+`reason`. A protected-name fixture (e.g. `README.md` in `temp-file-sweeper`) is byte-unpinned — content edits are verification-safe — while its existence, exact name, and extension are pinned by every case's `scanned` count.
- rg's treatment of the gitignored `.wrongstack/` tree is inconsistent: it has been observed both silently excluded (zero matches even with the path passed explicitly) and included (repo-root `files_with_matches` greps returning `.wrongstack\project-kit\...` paths). Never treat a zero-match grep over `.wrongstack/` as proof of no references; run the repo-wide grep anyway, check the truncation flag, and treat structural reading (`kit.json`, `main.mjs`) as ground truth.

## WebUI i18n

- Resolve the consumer set of a locale JSON (`packages/webui/src/i18n/locales/<lng>/<ns>.json`) by grepping the locales tree for `<ns>.json` — never via `codebase-incoming-calls` (the loader's dynamic import is invisible to it). There are exactly three consumer kinds: the i18n backend in `packages/webui/src/i18n/index.ts`, the fs-based test `packages/webui/tests/i18n/catalog-integrity.test.ts`, and `scripts/check-i18n-completeness.mjs` (npm `lint:i18n`).
- Count consumers of an i18n namespace by grepping the ns-prefix call syntax — ``t\(['"`]ns:`` (e.g. for `activity`) — not `useTranslation\(['"]activity`: components obtain translators via `useAppTranslation` and address keys as `t('ns:key')`, so hook-based greps return zero. Pair the `count`-mode grep with a `files_with_matches` companion for the exhaustive file list.
- Verify i18n guard specifics from each guard's own source before reporting locale-JSON blast radius; recalled rules may not be actual invariants. Verified coverage: `packages/webui/tests/i18n/catalog-integrity.test.ts` checks key parity, dangling refs, and hook wiring; `scripts/check-i18n-completeness.mjs` checks only missing/extra leaf keys vs `en`. Placeholder (`{{var}}`) parity in translated values is guarded by neither.
- Treat top-level section-count parity between a locale and `en` as corroboration, never proof — section order differs across locales and is irrelevant; only the gates prove leaf-key set equality.
- `activity` and `settings` are `DEFERRED_NAMESPACES` in `packages/webui/src/i18n/index.ts` — lazy Vite chunks with no inline English bundle, unlike the five small namespaces.

## Package-Specific Facts

- `SqliteSageStore` in `packages/sage/src/sqlite-store.ts` is a deprecated compatibility facade: route sage-storage work through `packages/sage/src/memory-port.ts` (`createSqliteMemoryPort`, `SqliteMemoryPort`) or the `sqlite-store-<area>.ts` sibling modules that hold the real logic. `packages/core/tests/architecture/memory-port-boundary.test.ts` regex-forbids `new SqliteSageStore(` outside the port layer — never propose constructing it directly in another package. When mapping external consumers of sage storage, use the `@wrongstack/sage` barrel symbols (`SqliteMemoryPort`, `createProjectSageMemoryPort`, `isSqliteAvailable`).
- Provider errors of the shape `<providerId> HTTP <status>` originate from `parseProviderHttpError` in `packages/providers/src/error-parse.ts`: message template, classification (`classifyProviderError`), retryability (`isRetryableKind`), and `retryAfterMs` extraction all live in that one function plus `packages/core/src/types/provider.ts`.
- Plugin `defaultState` is triplicated: `packages/plugins/src/plugin-audit-catalog/index.ts` is the single catalog source; the generated `packages/plugins/src/audit/index.ts` covers only published `@wrongstack/plugins` entries (zero `wstack-*` host plugins); `website/src/data/runtime-catalog.ts` hand-duplicates `defaultState` values and silently drifts unless edited in the same pass. Verify with a repo-wide grep of the plugin name, not the catalog module path.
- Disambiguate same-named services when tracing `incomingCallsService`, `outgoingCallsService`, `packageGraphService`, `fileGraphService`, or `symbolGraphService`: sync implementations live in `packages/tools/src/codebase-index/index-service.ts`; async wrappers with identical names are exported from `packages/tools/src/codebase-index/background-indexer.ts` and re-exported via the `./codebase-index/index` barrel. External consumers reach only the wrappers.
- Before mapping or editing any `project-server-*.ts` helper in `packages/tools/src/codebase-index/`, grep both the exported symbol names (`ServerQueryCaches`, `staleAwareRead`) and the module basename (`project-server-query-cache`). Some are extraction drafts never wired into `project-server.ts`, which still carries the inline original.
- `packages/core/src/storage/*` helpers typically have exactly one importer (e.g. `session-write-buffer.ts` ← `file-session-writer.ts`); one basename grep plus a `new X` grep completes the dependency picture.
- `@wrongstack/simpleui` grep hits are suspect until checked against `packages/cli/src/simpleui-dist.ts`, which resolves the package by path string (`resolvePackageJson('@wrongstack/simpleui/package.json')`) for static-asset serving — it looks like a barrel consumer but never imports the module. The simpleui barrel (`packages/simpleui/src/index.ts`) has zero in-repo importers by design; the package is consumed only as a built Vite `dist/` asset.
